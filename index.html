01

Why LLM Observability Is Different

Conventional distributed tracing is about latency and errors on deterministic code paths. LLM observability needs to track additional dimensions that don’t exist in HTTP microservices.

What changes

  • Token economics — cost is a function of prompt + completion tokens, not request count
  • Non-determinism — same input, different output; you must capture both
  • Quality metrics — latency alone doesn’t tell you if the answer was correct
  • Nested reasoning — tool calls, sub-agents, retrieval steps nest inside one “request”
  • Long inputs — prompts can be 128 K tokens; serialising them naively bloats your trace store

New signals needed

  • gen_ai.usage.input_tokens / output_tokens
  • gen_ai.usage.input_cost / output_cost (in USD)
  • Time-to-first-token (TTFT) separately from total duration
  • Model ID + version (models change quietly)
  • Finish reason (stop, length, tool_calls, content_filter)
  • Eval scores attached post-hoc to spans
The eval loop

LLM observability is incomplete without an evaluation loop: instrument → capture traces → run automated evals (LLM-as-judge, unit evals, human annotation) → attach scores to trace spans → alert on degradation. This is the core difference between “logging LLM calls” and true observability.

Trace Structure — Request, Completion, Tool Calls, Sub-Spans

An LLM trace is a tree of spans. The root span represents the user-visible operation; every model call, tool invocation, retrieval, and sub-agent call is a child span. The schema below is the Langfuse / Phoenix convention — also the target for OTel GenAI 1.x.

Trace root
user-request: “What is my invoice balance?”
L1 spans
LLM call — gpt-4o
retrieval — vector-db
L2 spans
tool: get_invoice_list
tool: get_invoice_detail
embed query
ann search (k=5)
L3 spans
LLM call — gpt-4o (final answer)
SQL: SELECT invoices WHERE …
SQL: SELECT line_items WHERE …

Span attributes by span type

Span kindMust carryShould carry
LLMmodel id, input tokens, output tokens, finish reason, TTFTfull prompt (sampled), full completion (sampled), cost, temperature, tool definitions
Tooltool name, input args, output, durationerror message if failed, parent LLM span id
Retrievalquery text, k, top-k doc ids, latencysimilarity scores, embedding model, index name
Chain / Agentstart/end time, statusintermediate steps, eval scores (attached post-hoc)
Trace ID propagation

Propagate traceparent (W3C Trace Context) across every async boundary, HTTP call, and queue message. Without this, tool-call spans from worker processes appear as orphaned root spans. Add traceparent to your task payloads and read it on the worker side before starting spans.

OpenTelemetry GenAI Semantic Conventions

The OTel GenAI semantic conventions (OTEP 0228, stabilised in opentelemetry-semantic-conventions v1.27+) define the standard attribute namespace for LLM spans. Using them means your traces are portable across any OTel-compatible backend.

AttributeTypeExample
gen_ai.systemstringopenai, anthropic, vertex_ai
gen_ai.operation.namestringchat, text_completion, embeddings
gen_ai.request.modelstringgpt-4o-2024-08-06
gen_ai.response.modelstringActual model used (may differ on fallback)
gen_ai.usage.input_tokensint1024
gen_ai.usage.output_tokensint256
gen_ai.response.finish_reasonsstring[]["stop"], ["tool_calls"]
gen_ai.request.temperaturedouble0.7
gen_ai.request.max_tokensint4096

Events (not span attributes) for content

OTel GenAI event model (OTEP 0228) — Python SDK
from opentelemetry import trace
from opentelemetry.semconv._incubating.attributes import gen_ai_attributes as ga

tracer = trace.get_tracer("my-llm-app")

with tracer.start_as_current_span("chat", attributes={
    ga.GEN_AI_SYSTEM: "openai",
    ga.GEN_AI_OPERATION_NAME: "chat",
    ga.GEN_AI_REQUEST_MODEL: "gpt-4o",
}) as span:
    # content goes in Events, not attributes — keeps spans small
    span.add_event("gen_ai.user.message",
        attributes={"content": user_text})        # may be redacted
    response = client.chat.completions.create(...)
    span.set_attribute(ga.GEN_AI_USAGE_INPUT_TOKENS,
        response.usage.prompt_tokens)
    span.set_attribute(ga.GEN_AI_USAGE_OUTPUT_TOKENS,
        response.usage.completion_tokens)
    span.add_event("gen_ai.assistant.message",
        attributes={"content": response.choices[0].message.content})
Events vs. attributes

The GenAI conventions deliberately put message content in events, not span attributes. Events are timestamped, can be streamed, and can be dropped by a head-based sampler without losing the span. This is the pattern that keeps trace payloads manageable when prompts are 50 KB+.

04

Langfuse — Open Source, Self-Host

Langfuse (MIT licence, langfuse Python/TypeScript SDK, v2.x) is a self-hostable LLM observability platform. Self-host with Docker Compose (Postgres + ClickHouse + Redis + web app) or deploy to Kubernetes via the Helm chart at langfuse/langfuse-helm.

Langfuse Python SDK — decorator-based instrumentation
from langfuse.decorators import observe, langfuse_context

@observe(name="answer-question")
def answer_question(user_id: str, question: str) -> str:
    langfuse_context.update_current_trace(
        user_id=user_id,
        tags=["support", "billing"],
        session_id="sess-abc123"
    )

    @observe(as_type="retrieval")
    def retrieve_docs(q):
        docs = vector_db.search(q, k=5)
        langfuse_context.update_current_observation(
            input=q, output=docs, metadata={"k": 5})
        return docs

    docs = retrieve_docs(question)
    completion = openai_client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role":"user","content":question}]
    )
    return completion.choices[0].message.content

Data model

Trace → Observations (spans, events, generations). Each generation carries token counts, model, cost, latency. Scores attach to any observation.

Evals

Built-in LLM-as-judge templates (hallucination, toxicity, relevance, correctness). Run on-the-fly or as batch over historical traces. Scores returned as floats 0–1 with an optional label string.

Self-host sizing

Postgres (4 vCPU / 16 GB) + ClickHouse (8 vCPU / 32 GB) handles ~500 rps of trace ingestion. Redis for queue; object store (S3-compat) for large payloads. ClickHouse compresses traces ~10:1.

Arize Phoenix — OTel-Native, Eval Built-In

Arize Phoenix (arize-phoenix v4.x, Apache 2.0) is built directly on OpenTelemetry. It speaks OTLP natively — no proprietary SDK required. Run it locally with phoenix serve (SQLite) or on-prem with PostgreSQL.

Phoenix — OTel auto-instrumentation (Python)
import phoenix as px
from openinference.instrumentation.openai import OpenAIInstrumentor
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

# Start Phoenix on localhost:6006
session = px.launch_app()

provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(
        OTLPSpanExporter(endpoint="http://localhost:6006/v1/traces")
    )
)
trace.set_tracer_provider(provider)

# Auto-patch the OpenAI client — zero code changes to call sites
OpenAIInstrumentor().instrument()

Phoenix eval framework

Built-in eval templates

  • HallucinationEvaluator — checks if completion contradicts context
  • QAEvaluator — correctness given reference answer
  • RelevanceEvaluator — document relevance to query
  • ToxicityEvaluator — content safety
  • SummarizationEvaluator — faithfulness to source

Running evals on traces

Pull spans from Phoenix’s REST API (GET /v1/spans?project=…), run the eval template (which itself calls an LLM), push scores back with POST /v1/evaluations. Scores appear alongside spans in the UI. Run as a nightly Airflow DAG or a real-time Kafka consumer.

OpenInference instrumentation library

openinference-instrumentation-* provides drop-in OTel instrumentors for OpenAI, Anthropic, LangChain, LlamaIndex, DSPy, and Bedrock. Each adds the OTel GenAI attributes and events automatically. Phoenix, Jaeger, Zipkin, or any OTLP backend will accept the same data.

Helicone & LangSmith — Hosted Options

When you don’t want to operate trace infrastructure yourself, two hosted platforms dominate: Helicone for gateway-level capture, LangSmith for LangChain-native deep tracing.

Helicone

How it works: swap your base URL to https://oai.helicone.ai/v1; add Helicone-Auth: Bearer sk-…. Helicone is a proxy that records every request/response, then forwards to OpenAI. No SDK changes required.

Features: request logging, token/cost analytics, rate limiting, prompt versioning, caching (exact-match). Self-hostable via Docker (HELICONE_S3_* env vars point at your own bucket).

Pricing: free to 10 K requests/month; $0.000100/request beyond (2025 pricing).

LangSmith

How it works: set LANGCHAIN_TRACING_V2=true and LANGCHAIN_API_KEY=ls_…. Every LangChain / LangGraph run automatically emits a trace. Works without LangChain via @traceable decorator or the REST API.

Features: nested run trees, dataset & eval harness, prompt hub, annotation queues for human feedback, regression testing across prompt versions.

Pricing: free tier 5 K traces/month; $10/seat/month + $0.50/1 K traces (2025 pricing).

Sampling Strategy — What to Capture

Capturing every trace in full detail at production LLM volumes is expensive and often unnecessary. A layered sampling strategy captures what matters without overwhelming your trace store.

Four sampling layers

Head-based sampler — probability-based, before any processing
↓
Tail-based sampler — keeps 100% of traces with errors or high latency
↓
Content sampler — drop prompt/completion text for repetitive high-volume routes
↓
Eval trigger — queue selected traces for LLM-as-judge scoring

ProbabilisticTraceIdRatioBased(0.05) — 5% of new traces5% general traffic
Always-on for errorsParentBased(TraceIdRatioBased) + tail filter in the Collector100% of error traces
Always-on for slowCollector tail_sampling processor with latency policy (> p95)100% > SLO threshold
User-tierBaggage attribute user_tier=enterprise; sampler reads baggage100% enterprise, 10% free
OTel Collector config — tail sampling with error + latency policies
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors-policy
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: slow-policy
        type: latency
        latency: {threshold_ms: 5000}
      - name: probabilistic
        type: probabilistic
        probabilistic: {sampling_percentage: 5}

PII Handling & Retention

Trace stores are often the most dangerous location for PII: prompts are rich natural-language text that carries names, email addresses, medical details, and financial data. Three obligations govern your approach.

Redact before export

Apply Presidio (or the gateway scrubber from Deck 01) to event content before the OTel BatchSpanProcessor exports. Use the OTel AttributesProcessor to replace gen_ai.*.content events with redacted copies. Never rely on the trace backend to do redaction — you have no control over what it indexes.

Retention policies

Store structural span data (tokens, cost, latency, model) indefinitely. Store full prompt/completion content for 30–90 days only, under a lifecycle policy (aws s3api put-bucket-lifecycle-configuration). Separate the payload store (S3-compatible) from the metadata store (ClickHouse/Postgres) so you can purge payloads without losing metrics.

Right-to-erasure (GDPR Art. 17)

Tag every trace with a user_id attribute. Build a deletion pipeline that, given a user ID, soft-deletes or scrubs all spans in Langfuse / Phoenix and purges matching objects from S3. Test this path quarterly — it will be called in production.

FieldClassificationAction
gen_ai.usage.*, latency, modelOperational metadataRetain indefinitely; no redaction needed
gen_ai.*.message.content eventsMay contain PIIRedact before export; 30-day TTL on payload store

What to Take Away

  • LLM observability ≠ distributed tracing. Token cost, non-determinism, quality scores, and nested tool call trees are first-class concerns that standard APM tools miss.
  • Structure your traces. Root span → LLM generation spans → tool/retrieval child spans. Propagate traceparent across every async boundary.
  • Use OTel GenAI conventions. gen_ai.system, gen_ai.request.model, gen_ai.usage.input_tokens. Put content in events, not attributes.
  • Langfuse is the best self-hosted option; deploy Postgres + ClickHouse, use the @observe decorator. Arize Phoenix is OTel-native and eval-first — use it when you already have an OTel pipeline.
  • Helicone (proxy swap, zero SDK) is ideal for quick capture with no code changes. LangSmith is the natural choice for LangChain/LangGraph shops.
  • Sample intelligently: 5% head-based + 100% errors + 100% slow traces. Tail-sample in the Collector, not the SDK.
  • PII in traces is a compliance risk. Redact before export, 30-day payload TTL, and implement a right-to-erasure pipeline before launch.
